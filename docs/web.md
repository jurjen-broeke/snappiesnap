# SnappieSnap in the browser

**Status:** first version, 2026-11-05 (0.15.1).
- **Tested:**
  - Chrome, headless, served from `localhost`. The page starts, Open picks and opens a file, Save and Export download it, and closing the page asks first when there is unsaved work.
  - Firefox, by hand, served by Apache on Ubuntu. Most things work as on the desktop.
  - The Apache settings below, checked with Apache 2.4: the right type, compression and caching.
- **Not yet tested:** Safari and Edge.

The web version is the desktop app compiled to WebAssembly: the same engine, the same views, the same commands. It runs entirely in the user's browser.
- Files are opened with the browser's file picker, or by dropping them on the page.
- Files are kept in the page's memory and saved as downloads.
- Nothing is uploaded: the server only hands out the program.

## Build

You need the Rust toolchain from `rust-toolchain.toml`, which includes the `wasm32-unknown-unknown` target, and [trunk](https://trunkrs.dev) (`cargo install --locked trunk`).

```sh
cd apps/snappiesnap-web
trunk build --release
```

The result is in `dist/web/`:
- `index.html`
- the program (`snappiesnap-web-<hash>_bg.wasm`, about 11 MB, 4 MB compressed)
- its loader (`snappiesnap-web-<hash>.js`, generated by wasm-bindgen)
- the icons

File names carry a content hash, so a new version never mixes with files a browser cached from an old one.

`trunk serve --release` builds, serves on `http://127.0.0.1:8080` and rebuilds on every change. Use it while developing.

CI builds the same folder in the `web-package` job and keeps it as `SnappieSnap-<version>-web.tar.gz`.

### One command, as CI builds it

```sh
cargo xtask web
```

This is the build above plus the packaging CI does: it writes `dist/web/` and packs `dist/SnappieSnap-<version>-web.tar.gz`, the archive to copy to the server. It needs `trunk` (`cargo install trunk`) and says so by name if it is missing. It is part of the development cycle for anything a user can see (AGENTS.md › Before you finish a task), so the browser version a tester loads is never more than one feature behind the desktop one.

## Serve

`dist/web/` is a folder of static files. Copy it to any web server; it can sit at the top of a site or in a subfolder, because all its links are relative. The server needs no build tools and no particular power: it only sends files. A small VPS, a NAS or an institute's web space is enough.

Two settings matter:
- **`.wasm` files must be served as `application/wasm`.** Most servers already do. With another type the app still starts, more slowly, and the browser console warns.
- **Turn on compression** (gzip or Brotli) for `.wasm` and `.js`. The program shrinks from 11 MB to about 4 MB.

nginx, for example:

```nginx
server {
    listen 443 ssl;
    server_name snappiesnap.example.org;
    root /var/www/snappiesnap;          # the contents of dist/web

    types { application/wasm wasm; }
    gzip on;
    gzip_types application/wasm application/javascript text/css image/svg+xml;

    # index.html always fresh; hashed files cached for a long time.
    location = /index.html { add_header Cache-Control "no-cache"; }
    location ~* \.(wasm|js)$ { add_header Cache-Control "public, max-age=31536000, immutable"; }
}
```

Caddy does all of this by itself: `file_server` plus `encode gzip`.

### Apache on Ubuntu

Unpack the archive into a folder of the site, for example `/var/www/html/snappiesnap`, which puts the app at `https://<server>/snappiesnap/`:

```sh
sudo mkdir -p /var/www/html/snappiesnap
sudo tar -xzf SnappieSnap-<version>-web.tar.gz -C /var/www/html/snappiesnap --strip-components=1
```

Put the settings in `/etc/apache2/conf-available/snappiesnap.conf`. A `.htaccess` file won't do, because Ubuntu's default `AllowOverride None` makes Apache ignore it.

```apache
<Directory /var/www/html/snappiesnap>
    AddType application/wasm .wasm
    <IfModule mod_deflate.c>
        AddOutputFilterByType DEFLATE application/wasm application/javascript text/javascript text/html image/svg+xml
    </IfModule>
    <IfModule mod_headers.c>
        # index.html always fresh; hashed files cached for a long time.
        <FilesMatch "\.(wasm|js)$">
            Header set Cache-Control "public, max-age=31536000, immutable"
        </FilesMatch>
        <Files "index.html">
            Header set Cache-Control "no-cache"
        </Files>
    </IfModule>
</Directory>
```

Turn it on:

```sh
sudo a2enmod deflate headers
sudo a2enconf snappiesnap
sudo apachectl configtest && sudo systemctl reload apache2
```

Check it, with the real name of the `.wasm` file in the folder. The answer should say `Content-Type: application/wasm` and `Content-Encoding: gzip`.

```sh
curl -sI -H 'Accept-Encoding: gzip' https://<server>/snappiesnap/snappiesnap-web-<hash>_bg.wasm
```

For HTTPS on a server with a public name: `sudo apt install certbot python3-certbot-apache`, then `sudo certbot --apache -d <server>`.

To update, empty the folder and unpack the new archive. Every version has new file names, so old files would otherwise pile up. Pages already open get the new version when they are reloaded, because `index.html` is never cached.

```sh
sudo rm -rf /var/www/html/snappiesnap/*
sudo tar -xzf SnappieSnap-<version>-web.tar.gz -C /var/www/html/snappiesnap --strip-components=1
```

To try a build on your own computer, run `python3 -m http.server 8000` in `dist/web` and open `http://127.0.0.1:8000`.

**Use HTTPS on a real server.** Browsers turn on WebGPU only for secure pages (HTTPS, or `localhost`). Without it SnappieSnap draws with WebGL, which works but is slower on large maps.

## What works, and what doesn't yet

Everything that works on a document works the same as on the desktop, because it runs the same code. That includes:
- the views: map, sequence, features, primers, enzymes, gel, alignment, history and notes;
- editing with undo;
- experiments.

The differences come from the browser:

| | Web version |
|---|---|
| Open | **Open** shows the browser's file picker. You can also drop files on the page. All the desktop formats open, including `.sslab` experiments. |
| Save | **Save** downloads the file under the name it was opened with. **Save As** asks for a file name; its extension picks the format. The browser puts downloads in its downloads folder. |
| Map export | Downloads the map as SVG or PNG. |
| Unsaved work | Stays in the page's memory only. Closing or reloading the page loses it, so the browser asks first while something is unsaved. |
| Folder panel | Not available: a web page can't see folders. Preferences says so instead of offering the switch. |
| Cloning | The Cloning experiment builds from the constructs open in tabs (its picker lists them under **Open now**), so open the vector and the insert first — or press **Try it with the sample constructs** in its first step, which opens pSample and demoInsert and fills the reaction in for you. On the desktop the same picker also lists the files of the open folder. |
| Align | Both alignments reach files without a folder. **To this sequence** takes the sequence from **a tab** (any other open document) or from a file chosen with **Choose…**, as well as pasted text. **Multiple** lists the other open tabs to tick, and **Add files…** loads several files at once with the browser's picker; the files it loads are listed beside any from the open folder. On the desktop the same buttons open the native picker. |
| Check Reads | **Add read files…** opens the browser's picker and takes several traces at once. Reads already open in tabs are listed to tick as well, so a trace dropped on the page can be checked without loading it again. |
| Settings | Not remembered between visits yet. |
| Enzyme sets | Build one in the Enzymes tab (tick enzymes, name it, **Save as set**) or read a set file with **Import a set…**. Sets last for the visit: a page cannot write files that outlive it. |
| Desktop only, for now | Importing lab oligo lists and GFF3 annotations; building a feature library from a folder; saving gel images; downloading REBASE; checking for updates. |
| Agents | No control channel and no MCP. Use the desktop app or `snappiesnap-cli mcp`. |
| Internal errors | The desktop app recovers from an internal error. A browser can't, so the page shows a message and has to be reloaded. Work that wasn't downloaded is lost. |

## How it fits together

| File | Role |
|---|---|
| `apps/snappiesnap-web/src/main.rs` | Starts the app on the page's canvas, with the sample plasmid. Startup problems and internal errors are shown on the page. |
| `apps/snappiesnap-web/index.html`, `Trunk.toml` | The page, and how trunk builds it. There is no handwritten JavaScript. |
| `crates/ui-egui/src/web.rs` | The browser side, through `web-sys`: the file picker, dropped files, downloads, the page title, and the question before leaving. |
| `crates/ui-egui/src/web_files.rs` | The rules that don't need a browser, tested natively: safe file names, never replacing an open file, the Download prompt. |

The engine uses `MemoryFs` as its file system on the web (`crates/engine/src/platform.rs`). A picked file is copied there under its own name and opened with the ordinary `open` command. If that name is already taken, it gets a numbered name such as `p (2).dna`. Saving writes back to `MemoryFs`, and the app then hands those bytes to the browser as a download.

`cargo xtask wasm` (part of `cargo xtask ci`) runs clippy on the WebAssembly build of every core crate and of the web app. Code that exists only on the web is held to the same no-panic rules as the rest.
